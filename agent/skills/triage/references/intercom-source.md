# Intercom source

Follow this from triage Stage 1 when the source is an Intercom conversation instead of a Linear issue. The seven stages apply with these changes.

When the source is one Intercom conversation from the Slack intake, there is no Linear issue at the start, so Stages 1 to 4 run on the conversation. Stage 1 reads it with intercom `fetch` (a URL) or `get_conversation` (an id) in place of the issue, reads each screenshot yourself with `read_image`, since Intercom lists attachments without interpreting them, and calls `classify_ask` with the conversation text. Stage 2 resolves the Intercom contact's email. Stage 3 also searches the conversation for prior investigations. If the Slack request names no single conversation, ask for it once and stop. Intercom is read-only: the answer goes to the requester in Slack, never directly to the customer. Never create a placeholder issue and never ask for a Linear identifier. A money ask goes to billing-triage's Intercom source.

- File the customer report before Stage 5 when the evidence shows a `Bug` (a named file and function, direct production or runtime evidence, a counted blast radius) or a `Feature Request`: one linear `save_issue` on the Engineering team, titled with the claim minus customer identifiers, with the conversation URL and bounded context, `labels: ["intercom-sourced", "Customer reported"]` and `links: [{ url: <canonical conversation URL>, title: "Intercom conversation" }]`. Then run Stages 5 to 7 on it, where the regression check completes the four-item Bug bar.
- Otherwise do not manufacture engineering work. A Support/Product follow-up is filed only when a person must act: the same `save_issue`, then `route_ticket` with `state: "Todo"`, the `Support` project, Aaron Fraga, the same `links`, and both source labels. Record the case under `intercom:<conversation id>` with no project id and the live area as `primaryFeatureKey`; ordinary feedback with no finding is not recorded.
- The document adds `**Intercom source**` and `**Conversation context**` lines under `**Organization**`.
- The Slack reply follows the finding with a short block headed "Reply you can send": two or three sentences for the customer with no internal names and no system names. Omit it when the reply asks the requester for missing information, when the requester wrote "do not reply to the customer" or anything equivalent, or when the verdict routes to engineering with no customer-facing answer yet. When this investigation created a Linear ticket, end the reply with that bare identifier alone on the last line, never a URL; when it created none, say nothing about a ticket. Leave out assignees, routing, code paths, SQL, raw logs, system names, customer identifiers and memory status.
