# Critic review protocol

Do not load this reference unless `STAGE 4 COMPLETE: evidence record ready` existed before this file was opened and `decide_triage` returned `review.required: true`, or returned `decided: false` and the fallback decided anything but the unproven stop: without Jev's confidence every fallback route is checked, and `route_ticket` holds it until the critic settles. For a fallback decision, take `review.kind` from it (`duplicate` for a `Duplicate`, `billing_inbox` for an inbox error set aside as billing, otherwise `bug`, `platform_limitation` or `user_error` by classification) and its reason from the evidence. If either gate is absent, stop reading and return to the unfinished stage. This reference is the protocol for the document write, the incident-hotlane gate, the first review, one adjudication, the second review, and the block.

`review.kind` says what is being checked: `bug` (a `Bug` that is not a `Duplicate`), `duplicate`, `platform_limitation`, `user_error` (a closure with an evidence lane that could not run, or a failure the customer saw), or `billing_inbox` (an inbox error set aside as billing, not code). For every kind except `bug` the question is the opposite one: is this really not a bug, and is it really the same cause as the ticket it joins.

1. Write the investigation document now. Call `save_investigation_document` with `lane: "triage"` and the full document from the template in [reporting.md](reporting.md), with every Stage 4 lane, the Stage 5 decisions, the `**Confidence**` line from `decision.confidence`, and the line `**Review**: Pending critic`. Keep the returned `documentId` and `updatedAt`; the critic reviews that exact version. Once the review settles a version, approved or adjudicated, nothing may change it until routing is done. When Aaron has asked for read-only validation, write nothing to Linear: pass the document id and `updatedAt` as the literal marker `read-only` and carry the full document text in the critic message.
2. Only when `review.kind` is `bug`, load `incident-hotlane` and produce its assessment from the document. It changes nothing; its route, proposed label, workstreams, and blast-radius figures are inputs to the review and to Stage 6. If the route is `NEEDS_HUMAN_URGENT`, do not call the critic: set the document's `**Review**` line to `Stopped: NEEDS_HUMAN_URGENT` with the assessment under it, call `route_ticket` with only `issue` and `assignee: "Aaron Fraga"`, add a one-line comment that a possible high-risk incident is awaiting confirmation, leave the ticket's state, priority, and labels untouched, and skip to Stage 7 with nothing settled. That reply states only what is known, says a person is confirming it, and promises no action. In a read-only run, describe those writes instead of making them. Every other kind has no hotlane assessment.
3. Post nothing about the review to the attended thread. The challenge, corrections, and adjudication are recorded in the document, never narrated in the thread. In a Linear session, send the requester their answer now with `reply_to_requester` (the finding and the unblock, nothing about routing or review), then delegate: the review settles routing and the document, not the reply. If adjudication changes what they were told, record it in the document and correct it on their next reply. In a Slack session, if the turn has to end while the critic is still running, end it with one short line that the answer is coming, with no findings; apart from that line, the next message the thread receives is the final reply, sent only after the critic result arrives and Stage 6 is done.
4. Delegate to the `critic` subagent for the first review. The message's first line is exactly `Source issue: <id>` (for example `Source issue: ENG-123`), naming the ticket under review. The next three lines are exactly `Document: <document id>`, `Document updatedAt: <updatedAt>`, and `Commit: <the full 40-character SHA Stage 4 read, from the Code path section>`; a read-only run writes `read-only` on both document lines. The verdict is logged and the block below is counted against these four lines: a result whose `reviewed` echo names another ticket, document, version or commit is a failed review, not an objection. Then give `Review kind: <review.kind>: <review.reason>` and the proposed decisions (classification, unblock, handling path, state, priority, labels, the hotlane route and proposed label for a `bug`, and the master). Always name the master: the one the Stage 5 search chose with its match rationale, the duplicate target with why it has the same cause, or `none eligible` with the four axes searched. Name the two or three claims the decision turns on so the critic verifies those first; for a closure the first is that the ticket is not a code bug. The critic replies in its fixed JSON shape; pass no schema. Do not paste the document text unless this is a read-only run.
5. Read the result as a whole before acting on `verdict`; this reading starts the adjudication. An `APPROVE` counts only when `criteria_results` holds exactly one entry for each of the twelve criterion slugs with no slug missing or repeated, no criterion is `FAIL`, and `blocking_findings` is empty. An `APPROVE` with any `FAIL` criterion, a missing or repeated slug, or a non-empty `blocking_findings` is handled as a `CHALLENGE`. A result with an empty `criteria_results` is a review that could not start (the child names why in `summary`). A `reviewed.commit` of `unpinned` or anything but the full 40-character commit supplied, or a `reviewed` not echoing exactly the issue id, document id, and `updatedAt` supplied (or the `read-only` markers), means the critic's checkout or packet failed, not the evidence. A result that does not match the child's contract, a delegation error, or a timeout is a failed review. A failed review is not an objection.
6. On a valid `APPROVE`: keep the critic's echoed `document_updated_at` and `commit` and continue to Stage 6 with the decisions as approved. Do not touch the document: the handoff checks the version Linear holds against the one the critic reviewed, and the `**Review**` line is written only after routing, as Stage 6 describes.
7. On `CHALLENGE`, on `INSUFFICIENT_EVIDENCE`, or on a failed review: adjudicate once against the Stage 4 evidence record. Take each blocking finding, or the gap the critic named, with its named next check: re-run the evidence lane it points at and correct the evidence, never a decision field by hand. When the review could not run at all, re-check the pivotal claims directly against the recorded lanes. If the corrected cause or code path changed, run the `engineering-handoff` master search again and record its master in the evidence, so the second review checks the master that will be used. Then call `decide_triage` again with the corrected record and take every field it returns, including a changed classification, handling path, priority, labels or review kind, so the decisions change to what the evidence does support. First update only the relevant evidence and decision sections with the corrected facts, without adding settlement-summary clauses elsewhere in the document, save it, and read back its adjudicated-evidence `updatedAt`. Then save it once more with `**Review**: Adjudicated <that adjudicated-evidence updatedAt> at <commit>: <CHALLENGE | INSUFFICIENT_EVIDENCE | review failure>` followed by one short clause per blocking finding or the failure reason, each naming what settled it, and read back the final `updatedAt`. Those clauses occur exactly once, in the `**Review**` line. That final read-back `updatedAt` is the settled version the handoff checks, exactly as the critic's echo is on an approval; the earlier adjudicated-evidence `updatedAt` remains the audit reference in the `**Review**` line. In a read-only run, carry the corrected text inline with the `read-only` markers instead.
8. Second review, only after step 7: delegate to the `critic` once more, with the same first line and the same fields, naming the settled version and commit, and one added line that lists each objection and what settled it. Read the result by the step 5 rules.
   - A valid `APPROVE`: continue to Stage 6 with the critic's echo of the settled version and the settled decisions.
   - A failed review: continue to Stage 6 on the settled version and the settled decisions. A failure is not an objection.
   - An objection, after a first review that also objected: the ticket is blocked. Go to step 9.
   - An objection, after a first review that failed: it is the first objection, so settle it against the evidence the way step 7 describes, without a third review, and continue to Stage 6 on that version.
9. Blocked. The critic objected twice in a row, so a weak cause or closure is not routed, and a master is not attached or created. Save the document with `**Review**: Blocked <the second review's document_updated_at> at <commit>: <CHALLENGE | INSUFFICIENT_EVIDENCE> twice` followed by one short clause per open blocking finding, and read back its `updatedAt`. Then call `route_ticket` with only `issue` and `assignee: "Aaron Fraga"`: the support owner takes a ticket without a label change, and a developer may not hold one that is not labelled `Bug`. Name the area owner from the roster in [roster.md](roster.md) in the document and in a one-line comment saying the checks could not confirm the result and Aaron is bringing in that owner. Leave the ticket's state, priority, labels, project, and parent untouched, and do not load `engineering-handoff`. `route_ticket` refuses any other route for this ticket once it is blocked. The Stage 7 reply states only what is known, says a person is checking it, and promises no action. In a read-only run, describe these writes instead of making them.

The critic reads evidence and recommends; Foreman adjudicates once; a second objection blocks. An approval is not permission to skip readback.
