# Widget case set

`cases/` is the active replay dataset. `split.json` fixes the train/test membership of every active case. Cases in `cases-pending/` are not discovered by the replay eval and have no split membership.

Cases use scrubbed recorded tool results, except the hand-authored help-center cases, whose source run is null. Expectations describe the intended product behavior and are not changed just to match an observed replay. Tool budgets count investigator tool results, including customer clarification, and do not count front-door help-center reads. A budget of one permits one tool call; it does not require zero provider reads.

A run whose investigator made a read that no recording answers (a cassette miss, or any result not recorded verbatim) is not scored: the eval logs "not scored: N unrecorded reads: <tools>", the row carries `scored: false` and the tool names, and a tracked-only soft assertion named "replay coverage" states the unrecorded tools. Eve 0.54.2 rejects skipping after activity, so its verdict reflects the safety gates only; the loop counts only rows with `scored !== false`. Behavior checks are computed but are not asserted or counted for uncovered replays, and the claims judge does not run. Its leak and raw-field checks still run and still fail it, because a leak is a real failure whatever the replay coverage. A case that is often not scored should move to `cases-pending/` for re-recording.

## Pulling production candidates

`pnpm widget:candidates [--since <ISO date>]` reads completed production `widget_support_runs` (point `FOREMAN_MEMORY_DATABASE_URL` at production). Acquisity's two test workspaces and three internal workspaces are excluded by default; `--exclude-orgs <uuid,uuid>` and `WIDGET_CANDIDATES_EXCLUDE_ORGS` add exclusions. Bounded SELECTs page by whole conversations and flag help-center misses, requests for a person, handoffs, gate rewrites, customer pushback and investigations that only asked a clarifying question. Each flagged conversation gets one entry in a review file under the gitignored `.eve/widget-candidates/`, which holds raw customer text. Each flagged investigation goes through the existing scrubber directly into `cases-pending/candidate-<run id>.json` with empty expectations, using `widget:case`'s `--output-dir` option; its default remains `cases/`. Terminal output shows run provenance, summary counts by signal, and fixed conversion failure classes, never child error text. Diagnostics and conversion recovery state stay under `.eve/widget-candidates/`: transient failures retry on the next pull without rewriting reviews, and leak refusals are recorded as terminal. `state.json` remembers the read cursor, so `--since` is needed only the first time. Each pull reads runs completed up to a minute before it starts, so a run still committing is picked up by the next pull. An immediate rerun after a successful pull flags no new conversations; it only retries conversions still pending from a transient failure, and runs that completed since add their own candidates.

## Front-door cases

The front door answers with the guide lane (`agent/lib/widget-chat.ts`): one streamed `kbChat` call (google/gemini-3.6-flash, Google AI Studio first; `WIDGET_CHAT_MODEL` overrides it) with the whole product guide as a cached prefix, started while the router scores the message and dropped on a handoff or a refund or ticket redirect. `WIDGET_CHAT=legacy` returns the front door to the help-center writer in `agent/lib/widget-kb.ts` for one release. The guide, `agent/lib/widget-product-guide.ts`, is generated from the help center with `pnpm widget:guide --repo <acquisity checkout> --ref <commit or branch>`. Retrieval, an article read tool and a grounding check after the reply were measured in rounds 2 to 4 and dropped: none lowered invented facts, and each cost time.

The guide regenerates on its own (ENG-15025). Acquisity's `docs-guide-trigger` workflow sends `docs-changed` with the commit SHA to this repository whenever `apps/web/content/docs/**` or `apps/web/lib/sidebar/catalog.ts` changes on its `main`, and `.github/workflows/widget-guide.yml` checks Acquisity out at that commit, runs the generator and opens or updates one PR on `bot/widget-guide` naming the commit, the regenerated sections and the run cost. It never merges. Each model call's output is stored as data outside the bundled agent tree in `scripts/widget-product-guide.cache.json` under a hash of its model, prompt, sidebar and articles, so a rerun calls the model only for batches whose inputs changed (a sidebar catalog change changes every batch's prompt), and a run that changes nothing leaves the files as they were and opens no PR. The workflow runs generator code from trusted Foreman main, loads only validated JSON cache data from an existing bot branch, and skips committing or pushing when the result matches the pending PR. The cache starts empty: the first automated run is a full bootstrap (about $2 reported cost), not an incremental update; no seeded cache is committed with the automation. Automatic dispatches require a commit in Acquisity main history. Run the workflow by hand with an optional `sha` (default Acquisity `main`); set `allow_other_ref` explicitly to use a commit or ref outside main history, and `full` to regenerate every section; locally, `--full` does the same. Each batch has one three-attempt budget covering transport errors, truncation and invalid sections; terminal errors name the batch and failed runs write no partial guide. Logs and the PR body distinguish model attempts from successful responses and report known response cost as reported cost, since failed requests may have cost more. Checkouts retain no credentials, and documentation symlinks and paths outside the extracted docs tree are rejected. The availability and entry-point lines at the top of `scripts/widget-product-guide.ts` are checked in the app by hand, and the PR body says to recheck them when the catalog or `apps/web/lib/features.ts` changed. Secrets: Foreman needs `AI_GATEWAY_API_KEY` and `WIDGET_GUIDE_TOKEN` (reads Acquisity, pushes the branch and opens the PR on Foreman; the default `GITHUB_TOKEN` cannot read the private Acquisity repo, and a PR it opens would not start `validate`), and Acquisity needs `FOREMAN_DISPATCH_TOKEN` (contents write on Acquisity/Foreman, which `repository_dispatch` requires).

`pnpm widget:case <run id> production <name>` also converts a front-door run: give it the run's UUID from `widget_support_runs` instead of a `wrun_` id, with `FOREMAN_MEMORY_DATABASE_URL` pointed at the read-only production role (`npx tsx --env-file=.env.prod-reader scripts/widget-case-from-run.ts ...`). The case's `question` is that run's message with the conversation's earlier turns rendered the way the router reads them (the last 8 messages, 2,000 characters each, as the app sends them), and replay splits it back into `question` and `history`. Help-center citations and screenshot images are not replayed; a screenshot reaches the case as the image model's reading, which production stored in the message. The scrubber runs unchanged, and the source run id is null because a run UUID is identifier-shaped. Names in free text are not something the scrubber can find, so each case was read and its people, businesses and workspace names replaced by hand with `Name N` and `Company One`.

The 40 `fd-` cases come from every customer widget run created from 2026-10-02 to 2026-10-07 23:00Z (161 conversations; the two test workspaces and the four internal workspaces excluded). Each case scores one front-door turn with every earlier turn as history, and no conversation gives more than one case. Selection, in this order: eight known failures from the 2026-10-07 analysis, by name, each scored at the turn where it happened ("which feature or page" re-asked after the feature was named, twice; a verbatim repeat; a solo owner answered about team invites; "do I need pro" asked a sixth time; Calendly, the personal access token and the plan options asked and missed); then both member conversations; then the first three conversations with a screenshot turn and the first four with an advice, strategy or copywriting ask (`rewrite|write|copy|copywriting|should i|strateg*|advice|make money|my niche|what can i present`); then by recorded path 5 asked_for_human, 4 kb_miss, 4 clarify, 4 chat, 3 explain (only one was left unused) and 5 kb; then multi-turn conversations until 12 cases have 3 or more turns (already met). "First" means ordered by the SHA-256 of the conversation id, and within a conversation the last front-door turn that fits the stratum is scored. `tags.lane` keeps the path production took. `split.json` puts 30 percent of each stratum, by SHA-256 of the case name, in test.

Claims come from the customer's need, never from any reply. Advice, strategy, copywriting and copy-review asks expect a friendly referral to the AI Consultant (the Chat toggle at the top of the left sidebar) and no advice or copy (Aaron, 2026-10-07). An explicit ask for a person expects `lane: "human"`, which the lane grader checks; other front-door cases leave `lane` unset, since which writer answers is not the expectation. Every judged answer also gets the `invented` claim (no invented product fact or promise), and a case with earlier turns gets `reask` (no re-asked detail) and `context` (answers the latest message). The `repeat` grader fails a reply that matches the previous assistant turn after lowercasing and dropping punctuation and spacing.

The judge reads each cited article live from the help center. `WIDGET_JUDGE_DOCS=<checkout>/apps/web/content/docs` makes it read the same slugs from a local docs tree instead, for judging against docs that have not shipped yet (ENG-14932 judges against Acquisity PR 6965, the docs the product guide is built from). `WIDGET_JUDGE_NAV=<file>` adds the app's navigation (the product guide's "## Navigation" section, checked in the real app) as one more source on every reply, so a sidebar or menu path it supports is not counted as invented (ENG-14932 round 3, Aaron 2026-10-08).

## Investigate cases

The `inv-` cases come from every production investigation (`widget_support_runs` with a `wrun_` session) from 2026-10-02 to 2026-10-09 04:47Z, before and after the ENG-14841 toggle: 188 runs. Team inbox runs and the two test workspaces were excluded, leaving 154 customer runs in 73 conversations. Eight conversations already have an investigate case, and three could not be converted (the leak check refused their only run). Of the remaining 62, four gave no case: three stated no problem, and one repeated `inv-asks-for-human-agent`. Each of the other 58 gave one case at the turn that best states the conversation's problem (one was later removed: its workspace is internal, Aaron 2026-10-09), converted with `pnpm widget:case <wrun id> production <name> --output-dir <dir>` and scrubbed by hand like the `fd-` cases. Expectations come from the customer's need and the recorded tool results, never from a reply. 32 replayed with zero unrecorded reads and are active; 25 are pending below.

Every investigate case sets `expectations.causeType`: `user_error`, `platform_limitation`, `bug` or `unclear` (the evidence cannot tell), from what the recorded evidence shows. For a user error or a platform limitation the judge adds the `fix` claim: the reply gives the product steps or the workaround, not only the diagnosis (Aaron, 2026-10-09). `split.json` puts 30 percent of each cause type, by SHA-256 of the case name, in test.

The claims judge also sorts every reply sentence saying something could not be confirmed, checked or was not available into `tool_gap` (data about the customer’s own Acquisity workspace that no widget tool reads, with a short name for the missing capability), `unused_capability` (a tool covers it but the investigator did not call it or lacked an input it could have asked for), `tool_failure` (a read errored or came back empty) `real_unknown` (the data does not exist) or `out_of_scope` (data the widget investigator must not have: another workspace or organization, the customer’s external bank, card issuer or mailbox provider records, or Acquisity-internal operations), stored as `gaps` on the judge record. The judge receives descriptions and input schemas from the actual tool definitions. The admission is never suppressed; a tool gap is fixed by adding the capability. Unused capabilities are ranked separately as investigator misses. Out-of-scope refusals are listed separately and do not count against no tool gaps.

`pnpm widget:judge scorecard [<eve eval dir>...]` (default: the newest `.eve/evals/` run) reads each run's replay rows and judge records for the active investigate cases and prints plain pass rates: found the real cause, nothing made up, answered what was needed (overall and per cause type), handed off only when needed, no leaks, stayed in budget (under the 14-call cap), no tool gaps, and first and final customer message time at p50 and p90 over scored replays only (measured at the eval's 3-second poll; progress is not a reply), then each failing leak check by case name, run directory and check name (never leaked text), and the tool gaps, unused capabilities and out-of-scope refusals ranked separately. A scored replay with no answer fails the answer goals. Missing judge records or required verdicts are reported as missing coverage in the header, remain in the denominator, and prevent complete hit/miss reporting. Answered what was needed requires context and reask verdicts when those claims apply. Several directories pool their replays; repeat `--judge-dir` once per eval directory in matching order to pool separately rejudged runs. Targets (`SCORECARD_TARGETS` in `agent/lib/widget-judge.ts`, agreed 2026-10-09): found the real cause 90%, nothing made up 95%, answered what was needed 90%, handed off only when needed 90%, no leaks 100%, stayed in budget 95%; reply time is read against a final reply under 60 s typical and 120 s slowest; no tool gaps gets a target once its trend is known. Hit or miss is withheld while judge coverage is missing.

`pnpm widget:judge rejudge <eve eval dir...>` re-judges saved replies without replaying, using the saved JudgeRecord evidence when available and the active case cassette otherwise. It makes one paid judge call per scored answer and re-reads cited public articles as normal judging does. It writes a separate judge directory per eval run and prints the matching `scorecard <eval dir> --judge-dir <new judge dir>` command. Legacy rows recover their answer and citations from the saved outcome log. A failed judge call is listed by case and run, remains missing coverage, and does not stop later rows. Re-judging does not change the original judge records or eval results.

## Live re-runs

Replay cannot prove a tool-gap fix, because a new or extended read has no recording. `pnpm widget:live <wrun id...> [--server <url>]` re-runs production investigations against the customer's own workspace (ENG-15026). Start a local `eve dev` with `WIDGET_LIVE=1`, no `VERCEL_ENV`, `.env.local` for Executor and `FOREMAN_DIAGNOSTICS_SECRET`. Live mode refuses every Vercel environment, including Preview; replay retains its existing Preview behavior. The runner requires `.env.prod-reader` for read-only production run lookup and Vercel CLI auth for stream decryption. Set live/replay flags only on the server, not the runner. The server must be an HTTP loopback origin (default `http://localhost:2000`); the runner checks its authenticated, data-free live-mode endpoint before sending a recorded scope or customer message, and refuses redirects.

The runner shares `scripts/widget-run-stream.ts` with `widget:case`. It compares each recorded read's exact input against its new output, ignoring only `observedAt`, key order and null fields as replay does. Failed or unavailable recordings and re-reads, including partial source failures, are excluded and listed as unverifiable. Actual comparable changes mean `state moved`; complete, nonempty unchanged evidence means `steady`; empty or incomplete unchanged evidence means `unverifiable`. Only steady evidence permits a future cause grade. Capability stays blank until ENG-15024's classifier replaces the named `gapSentences` seam; the report prints the original reply's limitation sentences beside the new reply.

The staff path keeps the result team-only. The local harness stamps the recorded original date, replaces every run-store dependency with filesystem persistence under `.eve/widget-live/runs/`, and uses the shared `replayable` ticket stub. No external database writes or Linear ticket writes occur, regardless of the server's database URL. Local store transactions use a filesystem lock with a five-second acquisition deadline and atomic replacement; after a process dies while holding the lock, stop the server before removing `.eve/widget-live/runs/lock` to recover. All raw evidence and results remain under the gitignored `.eve/widget-live/`; printed text passes through the existing scrubber and leak check, and is withheld if identifiers remain.

Date enforcement lives at the tool boundary, not just in a prompt. For an omitted billing `creditWindow`, the ledger reads the original UTC conversation day, from midnight inclusive to the next midnight exclusive. For an owned campaign's omitted `startDate`/`endDate`, outreach metrics read seven calendar days ending on that original day, both ends inclusive. Explicit windows are preserved. Campaign listing has no historical date filter, and billing's current/lifetime balances and Stripe lists remain current even when its ledger is pinned. The exact-input drift re-read preserves the recorded input, including implicit moving windows; the report marks those calls so current default-window comparisons are not mistaken for pinned historical evidence. `widget_job_failures` and `widget_generation_diagnostics` (`since`), `widget_lead_pipeline_status` (`sinceDays`) and `widget_sdr_thread_status` (30 days) only take windows ending now; other authored tools take no absolute date input.
