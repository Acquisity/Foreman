# Triage replay

This folder scores Foreman's triage against what people decided later (ENG-16049). It replays settled ENG tickets through today's triage code and checks the verdict, classification, handling path, project, owner, duplicate, master and root cause. A field the label leaves null is unscored, except the duplicate, where null means not a duplicate. Every Foreman triage change (ENG-16055, ENG-16056, ENG-16061) shows it helped here before it ships.

## What's here

- `cases/<ENG-id>.json`: 150 frozen cases. Each holds the ticket as it was first filed (scrubbed), its intake lane and stratum, the Acquisity commit on main when it was filed, and a snapshot of related issues as they were then. Each also carries `asFiled`, the source ticket's assignee, project, labels, parent and priority as first filed (the value before the first later change in the issue's history, or today's value if it never changed), which the replay seeds so a closure that keeps the owner scores right; a case without it would seed the ticket cleared. Every snapshot field is rebuilt from issue history as of the case's creation, or reads `unknown`. A train case's snapshot entry for a held-out ticket reads `unknown` for state, assignee, labels and parent, so the train inputs carry no held-out outcome; the cohort test fails if one does.
- `cohort.json`: the cohort's SHA-256, taken over the case files and the four frozen lists (`frozen/*.json`), so editing a frozen list is a new cohort too. A result scored against a different cohort is refused.
- `denylist.sha256.json`: SHA-256 hashes of customer, workspace and person names, with no names in clear text. The lower-cased text is split into tokens (`/[a-z0-9&]+/`), and the cohort test hashes every window of 1 to 6 tokens in every case, train label and frozen file; a window in the list fails the test and prints only a hash prefix. Our staff and our own company names are left out. A name found later is added as a hash here, and the cases are scrubbed (a case change makes a new cohort hash).
- `split.json`: train and held-out ids, split by incident group, so tickets that share a master never land on both sides. Devin's replay (ENG-16057) and the fix memory (ENG-16059) use this same split.
- `labels/train.json`: labels for the train cases only. Held-out labels never sit in this repository: the trusted scorer reads them from a file outside it, and the seal test fails if any other code names that file.
- `frozen/`: the ENG projects, labels, users and workflow states the replay answers from. Every entry carries its Linear `createdAt` (read 23 Oct 2026), and the replay answers only entries created before the case. An entry without one has unknown case-time membership: the replay leaves it out, the run records the list, and the scorer puts that case apart from the main score. Projects also carry `completedAt` or `canceledAt` when Linear has one, and labels their group, such as `Root Cause`. Users came from Linear's active users, so a person deactivated since then is missing, which can only make an owner miss, never leak an answer. Users carry the roster's email where `agent/skills/triage-handling/references/roster.md` has one, so routing by email resolves; the other users have no email on record here.
- How it was built: read-only scripts over Linear history and `gh`, run 23 Oct 2026. They write held-out labels and cache raw customer text, so they live outside this repository, with the held-out labels, in the ENG-16049 task folder (ask James). The cohort is frozen by `cohort.json`; rebuilding it means a new cohort hash and a fresh baseline.

Every label carries `outcomeAt`, the time of its latest human outcome, rebuilt from Linear history, comments and `gh` (null only on an insufficient label with no human source). Labels come only from human outcomes: a merged fix PR (its diff's files and functions first, then its Root Cause text), human state changes, human comments, billing actions, and closures nobody reopened within 30 days. Foreman's own document is never a label source. A confirmed non-bug closure that a person explained (a user error, a platform limit, an unpaid account) keeps that explanation as its root cause, with no files or functions, and the judge grades it against the explanation instead of a code place (14 train labels carry one today). The rule: a label that is not insufficient, routes (not `unproven`), is not a Bug and has no fix PR takes the sentence of its notes in which staff or the requester said, found, confirmed, explained, saw or removed something (not that it was fixed or resolved) as its cause. Re-swept 23 Oct 2026: it adds one train label (ENG-14523) and none in the held-out set. A case with no clear ground truth is labelled `insufficient` and scored apart.

## The replay boundary

A replay server runs with `TRIAGE_REPLAY=1`. The whole process then:

- refuses to boot with `VERCEL_ENV=production`, a widget replay or live flag, `FOREMAN_MEMORY_DATABASE_URL`, or a warm sandbox snapshot (its checkouts and Git objects hold newer code);
- answers every authored Linear operation from a simulated store per case (the ticket as filed, no later comments; documents, routes and relations the run writes stay in the store);
- gives replay sessions `read_triage_replay_issue`, `comment_triage_replay_issue`, `create_triage_replay_issue` and `list_triage_replay_catalog` (the open projects and Root Cause labels Stage 5 needs, as of the case, from `frozen/`) in place of the closed Linear connection, and keeps `reply_to_requester` and `record_investigation_case` in the store, so the normal procedure can finish;
- strips provider-managed tools such as web search from every root model call, so no search runs;
- fails every other provider read closed and records it as an evidence miss, including reads the Executor walls refuse before the typed client and calls to the closed Executor connection;
- denies the Executor MCP tools at the connection and the GitHub tools, and blocks outbound HTTP except the model hosts, Blob, the sandbox control plane and OIDC;
- opens sandboxes with no network, and gives `prepare_repository` and the critic's `checkout_commit` only a `git archive` of the case's commit, with no history;
- cancels the turn when the model asks for a tool the replay policy doesn't allow (`agent/lib/triage-replay/tool-policy.ts`), or at `TRIAGE_REPLAY_MAX_STEPS` model steps.

Every store answer, tool result, subagent result and loaded skill (root, critic and vision all mount the replay hook) is kept whole with its provenance: `seeded` (from the case or outside evidence) or `generated` (written by this replay). The scorer's leakage check reads only seeded inputs, so Foreman's own correct document read back isn't counted as leakage. The scorer's leakage check is conservative because it can't tell where text came from. Text the run read from its sandbox (`bash`, `read_file`, `grep` and the other sandbox tools) could be the pinned code, a supporting skill reference file, or something the run wrote to scratch, and it was three times wrong to guess: tracking the run's writes, then archive membership, each either flagged a clean run or cleared a planted leak. So any input a tool, skill or subagent returned that wasn't Foreman's own draft counts, whatever the tool: a flagged fix commit (every distinct SHA token, prefix or full), PR reference, PR title or body phrase, or root-cause phrase marks the whole case leak-suspect. Tool output is stored as JSON, so the scorer reads its escaped line breaks as spaces and a phrase split across lines still matches. A leak-suspect case is left out of the main rows of both splits and scored apart (every run of it), and the scorecard prints the suspect count and the score twice, once with every suspect counted as a failure and once as a pass, so the downward bias from false alarms stays visible; `scores.json` carries the same bounds. The scorer no longer exits 1 on a leak, because suspects are expected. On a case whose fix merged before triage, a hit is reported as available at triage, not a leak, only when it is a fix commit, PR number or PR title, in evidence timed at the case's creation (the pinned code or the as-of snapshot), and the PR merged before the case was filed. A root-cause phrase or PR-body text always counts.

No image or PDF reaches a replay model. A case seeds its attachment kinds, never the image bytes, and the egress wall blocks Linear's upload store, so any image or PDF a tool returns (bytes in the result, or a `mediaType` such as `read_file`'s `file.mediaType` that eve loads for the model, at any depth) didn't come from the case as filed: the hook cancels the turn and the run ends as a boundary error. That rule stands in for reading text out of images, which the leakage scan can't do.

## Running a replay

A replay costs live model calls: an Opus triage, the critic and Jev per case. It runs only after James approves the spend and Aaron names where it runs. The server holds the spend limits, not the runner:

- `TRIAGE_REPLAY_CONFIRM=1` and `TRIAGE_REPLAY_RUN_ID=<approved run id>` must be set on the server;
- `TRIAGE_REPLAY_MAX_RUNS` (default 3) caps starts for that run id, reserved and admitted together, counted in a Blob ledger, so restarts don't reset it. Each ledger change is a conditional write on the ledger's version, so racing starts can't pass the cap, and a ledger that keeps changing refuses the start;
- `TRIAGE_REPLAY_MAX_USD` is the run's hard model-spend cap, and `TRIAGE_REPLAY_EST_USD_PER_CASE` the estimated spend of one case. Both must be set, or every start is refused. Each start reserves its slot and charges the estimate in one ledger write, and a start that would take the charged total past the cap is refused. The reservation becomes an admitted start only once the session is dispatched, and a start that fails while seeding or dispatching releases its slot and spend, so the runner can retry the same case and run. Once the session is sent the start is permanent: the server records the dispatch in the case's store and confirms the ledger, each tried three times, and a later start of that case and run gets a 409 and settles the ledger instead of releasing the slot, so a retry can never refund a run that went out. A retry that reuses the store a failed start left behind restamps it with the retrying deployment's commit, start time and estimate before it sends. A second start of a case and run is refused while its reservation is under two minutes old, and a stale reservation is reused without charging again. The cap counts an estimate, not metered spend, because a replay can't see most of its model cost: Claude runs through the CLI proxy, which reports no cost, and Jev, `classify_ask` and the other model-only tools call their models inside a tool, where no hook sees the usage. Set the estimate from a measured smoke run;
- `FOREMAN_DIAGNOSTICS_SECRET` authorises the runner, and keys the replay's storage.

Replay state, the ledger, run inputs and the repository archives are private Blob objects. State and ledger keys are an HMAC of the server secret, archives carry a random suffix, and the server reads archives with its own Blob credentials. State is written only if it is still the version that was read, and each run input is its own object, so the root and the critic can't overwrite each other from separate invocations. The Blob store must accept private objects; a store that doesn't fails the replay closed.

A full held-out run starts 47 cases times `--runs`, so before it set `TRIAGE_REPLAY_MAX_RUNS=47` (or 47 times the runs) on the server, next to `TRIAGE_REPLAY_RUN_ID`; the default of 3 covers only a smoke run. The runner exits non-zero with a summary when any start is refused or any result can't be read back, because each missing row scores wrong.

```bash
# On the replay server: TRIAGE_REPLAY_CONFIRM=1 TRIAGE_REPLAY_RUN_ID=<approved run id> TRIAGE_REPLAY_MAX_RUNS=47
#   TRIAGE_REPLAY_MAX_USD=<approved cap> TRIAGE_REPLAY_EST_USD_PER_CASE=<estimate from the smoke run>
tsx scripts/triage-replay-archives.ts --acquisity <Acquisity checkout> --split heldout --out archives.json
tsx scripts/triage-replay.ts --url <replay server> --run-id <approved run id> --archives archives.json --split heldout
```

Then score the results with `pnpm triage:score`, the sealed label file (the usage line is at the top of `scripts/triage-score.ts`). A replay settles when its root turn ends, and it counts as completed only at a terminal outcome: a route the store applied to the case (after the critic settled, when the decision needs review), a billing route, or an unproven stop with its document saved. The final answer is the last decision for the case plus what the store applied to the case ticket (project, assignee resolved to a person, duplicate relation, parent as master), never a requested route. Every result records the Foreman commit the server ran (`VERCEL_GIT_COMMIT_SHA`, or `unknown` when the deployment names none), when the replay started and the estimated cost charged to it; the scorecard prints them, and the scorer refuses results from more than one commit, so a baseline and a candidate are never scored together. The scorer scores every case in the split, and every run number its results hold for it (`--runs` sets the expected count and must be at least 1; a result above it is refused, never dropped): a missing result, a failed or cancelled run, or a boundary error counts as wrong on every field, and the completion and evidence-miss counts print beside the scores, so a change can't score better by finishing fewer cases. There is no settling window (decided 23 Oct 2026): a case whose human outcome is young counts in the main rows, and a reopening or unlink after the label was written is not seen. Some cases are scored apart, each in its own row beside the main score and never in it, in this order: a description edited after filing (`descriptionEditedAfterCreate`, so later guidance sits in the input), a case whose run answered from a frozen list entry with no creation time, and a case flagged `needsProductionData`, because the replay has no production evidence to give it.

## Judge calibration

The root-cause judge is calibrated the way the widget judge is. `--calibration <path>` reads a person's grades from a file outside this repository: one entry per row, `{ "row": "ENG-123#1", "documentSha256": "<sha256 of the run's document text>", "grade": "match" | "partial" | "wrong", "reason": "..." }`, the judge's own verdict shape plus the row and the document it graded. `--rerun` judges every row twice, so it needs twice the `--max-judge-calls`, and the scorer refuses before the first call when the cap is short. The scorecard then prints the judge's agreement with the hand labels (both passes on a rerun), the flip rate between the two passes, how many hand labels were measured, stale (a different document than the one labelled) or missing, and whether the ticket's bar is met: every label measured, at least 90% agreement and at most 5% flips. It prints counts only, never a hand label's grade or reason. Both flags need `--judge`.

## Live logging

Outside a replay, every triage now logs countable lines with the issue id. `triage.decision` logs each time `decide_triage` settles, unproven outcomes included, with `decision` set to `decide` for the first decision on that ticket and `adjudicate` for a later one, and again with `decision: route` whenever `route_ticket` writes a ticket (final outcome, classification, path, project, duplicate, assignee kind). A ticket with no Jev decision, because Jev failed and the skill decided, logs `outcome: skill` and `code: skill_fallback` with no classification or path; a route that passes `decide_billing`'s Support route logs `outcome: route`, the path `Support/Financial` and `code: billing`. Decisions are kept per ticket, billing ones included (`decide_billing` takes the ticket's `issue`), and the later decision for a ticket wins, so a route or verdict for one ticket never carries another's. A billing decision made before its ticket exists binds only to the ticket this session creates next through a tool Foreman can see, and is dropped when that creation fails or any ticket is routed first; a ticket created through the Executor connection is not seen, so its billing route logs `skill_fallback`. `critic.verdict` (verdict, failed criteria, blocking findings, or `failed`) logs when the critic settles, against the ticket named on the dispatch message's first line (`Source issue: ENG-123`); a critic call without that line logs nothing, rather than guessing from issue ids elsewhere in the message.
